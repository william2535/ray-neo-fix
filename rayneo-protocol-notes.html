The headline

Chrome's WebUSB refuses this device outright — protected class, because it's HID. That refusal is a browser policy, not an Android limitation. Termux with a wrapped file descriptor claims interface 0 without trouble.

Confirmed working: three-axis accelerometer readings over USB on Android, no root, no vendor SDK. Gravity magnitude measured 9.73–9.77 against a true 9.81.
Sensor work complete. Frame decoded, accelerometer verified, all three head axes recoverable from the gyro, and the device answers at 118 Hz. Enough to build a tracker on.

Descriptor

34 bytes, read via standard GET_DESCRIPTOR (type 0x22):

06 00 FF  09 01  A1 01
  09 02  15 00  26 FF 00  75 08  95 40  81 02   ; Input,  64 bytes
  09 03  15 00  26 FF 00  75 08  95 40  91 02   ; Output, 64 bytes
C0

A bare vendor pipe. No sensor usages, no report IDs, no feature reports declared. Nothing here hints at what the device does — the whole protocol is private.

03

How to talk to it

This is the key finding of the session, and it isn't obvious.

  • Commands go out on the control pipe as a HID SET_REPORT, not to the interrupt OUT endpoint. The same payload sent to endpoint 0x01 gets no reply at all.
  • Replies come back on interrupt IN 0x81.
  • Nothing is ever pushed. Passive listening returns zero frames forever. This wasted the first hour — the device only speaks when spoken to.
; control transfer
bmRequestType 0x21   ; host to device, class, interface
bRequest      0x09   ; SET_REPORT
wValue        0x0301 ; feature report, id 1
wIndex        0x0000 ; interface 0
payload       2 bytes

Polling at 20/s gave 599 replies in 30 seconds — a 100% response rate. It is completely reliable once you ask correctly.

04

Two frame types

Every reply is 64 bytes starting 99. Byte 1 is the type, byte 2 is 0x40 = 64 = the length.

Type 0xC8 — status

99 C8 40 00 | 12 23 48 00 | 00 19 00 32 13 51 35 33 ...
             ^ clock, LE   ^ constant

Clock in bytes 4–6 advances 1500 units per 50 ms poll. Everything after is frozen — likely firmware or model identifiers. Returned by 01 66 and friends.

99 65 40 00 | 36 3E 1D 41 | 5C 25 80 3F | 2F E6 03 3F | 00 F5 3E 3C | 40 B4 71 3D | 78 A5 CC 3D | 00 08 E4 41
   header    |   accel X   |   accel Y   |   accel Z   |   gyro X    |   gyro Y    |   gyro Z    | temperature
                  9.8277        1.0011        0.5152        0.0117        0.0590        0.0999        28.50
                        ^ seven float32, little-endian, from offset 4
  
Offset 4, not 8. There is no clock in the 0x65 frame — that only appears in 0xC8 status frames. Reading from offset 8 gives a plausible-looking gravity answer when the glasses lie flat, because accel X is near zero there. On the left side the two readings separate hard: offset 4 gives 9.89, offset 8 gives 1.12.

No calibration matrix needed. Y and Z are a rotated pair, so a sum and a difference recover both axes.

Across ten yaw samples Y and Z shared sign 10/10, mean Z/Y ratio 0.28 — an IMU sitting about 15° off square, as you would expect inside a temple arm.

06

Getting sensor mode

Sensor mode is not persistent. A fresh process gets type 0xC8 status frames. Something in a full sweep flips it into emitting type 0x65, and it reverts when the process exits.

What reliably worked: sweep XX 01 for XX across 00–FF, three sends each, ~40 ms read window. Sweeping 01 XX instead does not do it — that cost half an hour of confusion.

The enable is 00 01. The very first command in the sweep. One SET_REPORT of 00 01 flips the device into type-0x65 mode — no sweep needed, wake is instant.

Sensor mode still ends when the process does, so send it once at startup every session.

07

Environment

  • Termux and Termux:API both from GitHub. Play Store builds have a signature mismatch that breaks termux-api installs.
  • pkg install python libusb termux-api
  • libusb needs LIBUSB_OPTION_NO_DEVICE_DISCOVERY (value 2) before libusb_init, then libusb_wrap_sys_device on the descriptor. Android can't enumerate.
  • libusb_set_auto_detach_kernel_driver then claim_interface(0) — works, no root.
termux-usb -l
termux-usb -r -e "python -u SCRIPT.py" /dev/bus/usb/001/002
Argument order: termux-usb appends the descriptor after your own flags. Scripts must scan the argument list for the number rather than assume it's first.

Where to pick up

  • Build the tracker. Integrate yaw over time, add a dead-zone for drift, then smooth. The sensor side is done.
  • Confirm the yaw sign convention: which direction of turn gives a positive Y+Z.
  • Add recentre, dead-zone and smoothing once the axes are known.
  • For head-look in games: Shadow runs Windows, so head-to-mouse would work there. The obstacle is injecting relative mouse motion on Android, which normally needs root — check that before building toward it.
  • Only after all that does a fused orientation — and anything drawing a screen — become worth attempting.
Scope reminder. Even fully decoded, this yields a head-tracked floating screen. Head-look inside a game needs the game to accept an orientation input, which no Android title or emulator does. That part is Windows-only, and Mario Kart is out on every platform.
Everything here was measured on one device in one session. The vendor could change any of it in a firmware update. Treat the frame layout as observed behaviour, not documentation.
