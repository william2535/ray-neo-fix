Head Tracking
From Nothing RayNeo Air 4 Pro · Android · no root

Will Flood
Reverse engineering, protocol decoding, implementation and testing.
All work carried out on an Android handheld with the glasses in hand.

The RayNeo Air 4 Pro has no published Android SDK for its motion sensors, and no third-party tool existed to read them. In one session I established the USB command protocol from scratch, decoded the sensor frame, mapped every head-rotation axis, and built working head tracking that drives a real mouse cursor — on an unrooted Android device.

01

The starting point

The glasses connect to a phone over USB-C and act as a display. Inside them is an inertial measurement unit — accelerometer and gyroscope — used by RayNeo's own app. That app is the only software that can read it. There is no public SDK, no documentation, and no community driver for Android.

The first attempt was a browser probe using WebUSB. It failed:

cfg 1 if 0 (HID) .. refused
   The requested interface implements a protected class.

That refusal is often read as "this device is unreachable". It isn't — it's a Chrome policy that blocks HID interfaces on principle. Android's own USB stack has no such rule. Recognising the difference is what made everything after it possible.

02

Getting in

Termux with a wrapped file descriptor claims the interface without root. libusb must be put into no-discovery mode first, because Android cannot enumerate the USB bus from userspace.

libusb_set_option(NULL, LIBUSB_OPTION_NO_DEVICE_DISCOVERY)
libusb_wrap_sys_device(ctx, fd, &handle)
libusb_set_auto_detach_kernel_driver(handle, 1)
libusb_claim_interface(handle, 0)      -> success

The device descriptor gave nothing away: a bare vendor pipe, usage page 0xFF00, one 64-byte input report, one 64-byte output report, no report IDs, no sensor usages. Everything about the protocol was private.

03

The protocol

Three findings, each of which cost time to reach and none of which is obvious.

1
Commands go down the control pipe

Sent to the interrupt OUT endpoint, the device ignores them entirely. Sent as a HID SET_REPORT control transfer, it answers.

2
Nothing is ever pushed

Passive listening returns zero frames indefinitely. The device is strictly request–response. An hour was lost waiting for a stream that does not exist.

3
Sensor mode is not persistent

A fresh process gets status frames. One command — 00 01 — switches it into sensor mode, and it reverts when the process exits.

; the working call
bmRequestType 0x21   bRequest 0x09
wValue        0x0301   wIndex 0x0000
payload       00 01
; reply arrives on interrupt IN 0x81, 64 bytes
04

Decoding the frame

Two frame types exist, distinguished by byte 1. 0xC8 carries a status block with a running clock; 0x65 carries the sensors.

99 65 40 00 | 36 3E 1D 41 | 5C 25 80 3F | 2F E6 03 3F | 00 F5 3E 3C | 40 B4 71 3D | 78 A5 CC 3D | 00 08 E4 41
   header   |   accel X   |   accel Y   |   accel Z   |   gyro X    |   gyro Y    |   gyro Z    | temperature
                 9.8277        1.0011        0.5152        0.0117        0.0590        0.0999        28.50

Seven little-endian float32 values from offset 4. This was the hardest single detail. I initially read from offset 8, on the assumption that the sensor frame shared the status frame's clock field. It does not. The error is invisible when the glasses lie flat — accel X is near zero, so the remaining axes still produce a plausible gravity reading.

How it was caught. Cross-checking my decode against a second independent analysis surfaced the discrepancy. I then designed a test that separates the two readings: on its left side, gravity leaves the offset-8 plane. One layout holds 9.81, the other collapses.
left side, glasses still, 52 frames
  offset 4 :  |v| mean 9.89   min 9.85   max 9.92   MATCHES GRAVITY
  offset 8 :  |v| mean 1.12   min 1.09   max 1.16   does not match
05

Proving the accelerometer

A stationary accelerometer must read 9.81 m/s² in every orientation, with the vector pointing at the ground. Four held positions, hands off, several hundred samples each:

positionXYmagnitudevector angle
flat, lenses down8.245.299.7933°
nose down−3.849.069.84113°
flat again7.636.119.7739°
flat, lenses up−8.10−5.389.72214°
The decisive test. Inverting the glasses flipped both channels' signs with residuals of 0.14 and −0.09, and rotated the gravity vector 181° for a 180° physical flip. Nothing but a real accelerometer behaves that way.
06

Mapping the head axes

Each rotation isolated in turn, eight seconds per run, several hundred samples each.

movementgyro signature
pitch — noddingX alone, ±60°/s while Y and Z stay under 7
yaw — left / rightY large (±118), Z same sign at 28%
roll — ear to shoulderY and Z opposite signs, similar magnitude
held stillall three under 2.5°/s

Yaw and roll both land across the Y/Z pair because the IMU is mounted at an angle inside the temple arm. Across ten yaw samples Y and Z shared sign 10 times out of 10, mean ratio 0.28 — an offset of about 15°. Because roll splits them oppositely and yaw together, both are recoverable arithmetically, with no calibration matrix and no trigonometry:

pitch = gyroX
yaw   = gyroY + gyroZ
roll  = gyroY - gyroZ
07

Building the tracker

Raw rates are not head tracking. Four things had to be added.

  • Bias calibration. Two seconds stationary at startup establishes each axis's zero offset.
  • Dead-zone. Rates under 2°/s count as zero — a threshold taken from the measured noise floor, not guessed.
  • Continuous bias re-learning. Yaw has no gravity reference and drifts without correction. When the sensor reads still for a second, the bias estimate is nudged toward the current reading. Simulated over 30 seconds this reduced drift from 9° to 0.00°.
  • Sub-pixel accumulation. A slow 5°/s turn produces 0.508 pixels per tick. Truncating each tick to an integer would floor every one to zero and slow head movement would do nothing at all. The fraction is carried between ticks.
Accuracy: one second at a known 90°/s integrates to 89.5°. Half a degree over a full head turn.
08

Driving a real cursor

Injecting relative mouse motion on Android is normally said to require root, because /dev/uinput is root-only on a standard device. On this handheld it is not:

$ ls -l /dev/uinput
crw-rw-rw-. 1 uhid uhid 10, 223 /dev/uinput

Mode 666, and SELinux permits both the open and the UI_DEV_CREATE ioctl. A virtual mouse can therefore be registered from ordinary userspace Python. Verified by drawing a square with the cursor before any sensor was involved.

Result: head motion moves the system cursor, with no root, no vendor SDK and no custom kernel. Because the cursor is a real input device, anything that accepts a mouse accepts it — including a streamed Windows game.

10

Honest limits

  • Everything here was measured on one device. A firmware update could change any of it.
  • The 15° mount offset is specific to this pair and may vary between units.
  • The /dev/uinput permissions are a property of this handheld. On a standard Android phone this would need root.
  • Yaw is gyro-only, so it drifts. The bias re-learning largely handles it; a recentre control exists for when it doesn't.
  • This produces mouse and orientation output. It is not a full spatial-anchoring system.
