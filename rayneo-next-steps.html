00

Warm up

Three commands, one at a time. Each has a pass condition — don't move on until it's met.

termux-usb -l

Should print a path. Note it — after a replug it may be 001/003 rather than 001/002, and every command below uses it.

termux-usb -r -e "python -V" /dev/bus/usb/001/002

Should print a version in about a second. Accept the Android USB prompt.

ls

Should list rayneo_axes.py and the rest.

If termux-usb -l hangs, that's the Termux:API service, not our scripts. Exit Termux from the notification shade and reopen. If it still hangs, reboot the phone.
01

The main job

Find the missing 8.83 m/s². On the left side, ch0–ch2 total only 4.28 while the glasses are provably still. Gravity has to be somewhere, and no float channel holds it.

Most likely explanation: the third axis isn't a float. If it's a scaled 16-bit integer, the float decoder would render it as the exact 0.00 we keep seeing. rayneo_raw.py reads every offset as float32, int16 and int32 at once so the shape doesn't matter.

Get it across

cp ~/storage/downloads/rayneo*raw.py ~/rayneo_raw.py

Run A — left side

Glasses on their left side, hands off, then:

termux-usb -r -e "python -u rayneo_raw.py --hunt 8.83" \
  /dev/bus/usb/001/002

Prints three full 64-byte frames, which bytes changed, and any field anywhere in the frame reading near ±8.83.

Run B — flat, for comparison

Glasses flat lenses-down, hands off:

termux-usb -r -e "python -u rayneo_raw.py --hunt 8.83" \
  /dev/bus/usb/001/002
What proves it. A field that reads ~8.83 on its side and ~0 when flat is the third axis. One that reads 8.83 in both is a coincidence — ignore it.

Screenshot both. The hex blocks matter as much as the summary.

02

If run A finds nothing

Widen the net rather than repeating:

termux-usb -r -e "python -u rayneo_raw.py --hunt 8.83 --tol 2.0" \
  /dev/bus/usb/001/002

Also worth trying, in case the scaling isn't 1:1 — hunt the raw g value instead of m/s²:

termux-usb -r -e "python -u rayneo_raw.py --hunt 0.9 --tol 0.3" \
  /dev/bus/usb/001/002

0.9 g is the same tilt expressed in g rather than m/s². Some devices report one, some the other.

Still nothing? Then ch0/ch1 are probably a computed projection rather than raw axes, and the third component may genuinely not be transmitted. Send me the bytes that changed list from both runs — that narrows it faster than more hunting.
03

Then: confirm the gyro

Quick and worth having nailed down. Two runs with the existing script:

termux-usb -r -e "python -u rayneo_axes.py --n 14 --quiet" \
  /dev/bus/usb/001/002
runwhat to doexpected
1Dead still on the tablech3, ch4 near 0.00
2Rotate steadily and continuously through the whole 6sch3 or ch4 clearly non-zero

If run 2 shows movement on those channels and run 1 doesn't, that's the gyro confirmed and yaw is available.

04

Then: is ch6/ch7 a compass?

Same command. Keep the glasses flat and level throughout — only the heading changes.

  1. Flat, pointing one way. Run. Note ch6, ch7.
  2. Rotate 90° on the spot, still flat. Run. Note them again.
  3. Another 90°. Run.

If ch6/ch7 trace a circle while ch0/ch1 barely move, it's a magnetometer and you have absolute heading — which beats a gyro, since it never drifts.

05

Rules that save time

  • Type commands, don't paste. Pasting injected [200~ into commands twice and sent a duplicate line into a running script's stdin.
  • Hands completely off during sampling. If it says magnitude varied, the run is worthless — redo before reading anything into it.
  • Check the |v| column first. Near 9.8 means trustworthy. Anything else means you moved them.
  • Phone on charge. The glasses draw from it, and low battery gets Termux:API killed.
  • One variable at a time. Change the position or the flags, never both.
